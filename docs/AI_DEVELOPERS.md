# Elvin: правила для AI-розробників

Над Elvin одночасно працюють кілька AI-розробників. Цей документ потрібен, щоб ми не заважали одне одному і не ламали робочий сайт. Прочитайте його перед будь-якою зміною.

## 1. Головний принцип

```
Креслення → AI-аналіз → Wardrobe Engine → ЄДИНИЙ список деталей → 3D + специфікація + BAZIS
```

- **3D і BAZIS не будують конструкцію самі.** Вони лише показують чи експортують `wardrobe.parts`, які розрахував Wardrobe Engine.
- **3D не може рівномірно розставляти стійки чи полиці або вигадувати розміри.** Якщо деталі немає в `parts`, 3D її не малює.
- **Демо-режим із ручним введенням допустимий,** але має бути явно позначений як демо і не потрапляти в BAZIS.

## 2. Хто що робить

| Напрям | Відповідальний | Файли |
|---|---|---|
| 3D-перегляд, вигляд сайту | розробник 3D (ChatGPT) | `viewer.html`, `3d.html`, стилі в `index.html` |
| Розрахунок конструкції, правила, AI-розпізнавання, код BAZIS, тести | Claude | `engine/*`, `rules/*`, `ai/*`, `netlify/functions/*`, `tests/*` |
| Спільне | обидва | формат `wardrobe.parts` (розділ 3) і `index.html` |

Якщо потрібно змінити файл з чужого напряму, опишіть це в PR. Не переписуйте чужу логіку мовчки.

## 3. Формат даних (контракт між Engine і 3D/BAZIS)

`buildOrder(analysis)` з `engine/order-builder.js` (для одного корпусу — `buildWardrobe`) повертає:

```js
{
  ok: boolean,
  status: "READY" | "GEOMETRY_INCOMPLETE" | "ASK" | "ERROR",
  missing: [{ field, question }],          // чого бракує; показати технологу
  warnings: [string],
  project: { projectName, width, height, depth, material, materialThickness, ... },
  modules: [{ index, name, status, width, height, depth, parts }],   // лише якщо модулів кілька
  parts: [Part],                           // ЄДИНИЙ список деталей
  sections: [{ id, module, x_mm, y_mm, z_mm, size_x_mm, size_y_mm, size_z_mm }],  // порожні комірки
  geometryCheck: { ok, errors: [{ code, parts, message }] },
  bazis: { status: "DRAFT_CODE" | "PREVIEW_CODE_READY" | ..., script, productionReady: false }
}
```

**Part:**

```js
{
  id: "m2_shelf_1_3",        // унікальний (m<N>_ — префікс модуля)
  name: "POLKA",             // назва за стандартом фабрики, може повторюватись
  role: "side" | "bottom" | "top" | "shelf" | "partition" | "back",
  module: 2,                 // номер модуля, якщо модулів кілька
  x_mm, y_mm, z_mm,          // МІНІМАЛЬНИЙ кут габариту деталі
  size_x_mm, size_y_mm, size_z_mm,
  thickness_mm, material,
  edges: null,               // кромка ще не розраховується
  fits_into: ["side_left"]   // необов'язково: деталь стоїть у пазу цих деталей (ХДФ), перетин дозволений
}
```

**Система координат (одна для всіх):**
- **X** — ширина, зліва направо;
- **Y** — глибина, Y = 0 — це ПЕРЕД корпусу;
- **Z** — висота, від підлоги вгору;
- усі деталі паралельні осям, довільних поворотів немає;
- орієнтацію визначає вісь, по якій розмір дорівнює товщині: X — боковина чи стійка, Z — горизонтальна деталь, Y — ХДФ, фасад, цоколь.

**Для Three.js:** розміщуйте кожну деталь за центром: `x_mm + size_x_mm/2`, `y_mm + size_y_mm/2`, `z_mm + size_z_mm/2`. Пам'ятайте, що в Three.js вгору спрямована Y, тож висоту Elvin (Z) треба перенести на Y сцени.

**BAZIS:** перетворення осей (у BAZIS x — ширина, y — висота, z — глибина, перед — z = D) лежить лише в `engine/bazis-axes.js`. Не дублюйте його деінде.

## 4. Правила фабрики

- Усі правила зберігаються лише в `rules/wardrobe-rules.js`, зараз це версія 1.8.
- Не змінюйте правило без явного рішення власника продукту. Кожна зміна — окремий комміт, у повідомленні вказано дату рішення.
- Невідомий розмір = `null` і питання технологу. Не вигадувати, не ділити порівну, не «округлювати під себе».
- Рішення, які вже затверджені, і питання, які ще відкриті: `docs/ENGINE_AUDIT.md`, `docs/RULES_COVERAGE.md`, `docs/Elvin_pytannia_tehnologu.xlsx`.

## 5. Гілки й PR

- **`main` — робочий сайт.** Прямих коммітів у `main` не робити. Лише через PR після `npm test` і з дозволу власника.
- **`elvin-3d-test-v2` — тестова гілка.** Нова робота йде через PR у неї.
- Відкриті PR:
  - #9 — 3D-імпорт;
  - #10 — розрахунок, правила, AI-схема, модулі.
- В описі кожного PR: що змінено, які тести пройдено, що не перевірено.

## 6. Перевірка перед PR

```bash
npm test          # node --test tests/*.mjs — має бути 0 fail
```

- `tests/real-orders.test.mjs` звіряє Elvin з реальними замовленнями з GibLab. Якщо зміна ламає цей тест, вона неправильна, навіть якщо виглядає краще.
- Функції Netlify мають збиратися esbuild. Регулярні вирази з `\` пишіть уважно: раніше саме це ламало збірку.
- Сторінку перевіряйте в браузері: консоль має бути без помилок.

## 7. Чого не робити

- Не будувати геометрію в 3D чи BAZIS окремо від Engine.
- Не змінювати `main` напряму.
- Не змінювати правила фабрики без рішення власника.
- Не вигадувати розміри й конструкцію, яких немає на кресленні чи в правилах.
- Не позначати результат як готовий до виробництва: `productionReady` завжди `false`, дозвіл дає технолог.
- Не зберігати в репозиторії особисті дані клієнтів (імена, телефони, адреси). Репозиторій публічний.
